# Skills bundle

Agent Skills that teach Claude to use the ESPN fantasy-football MCP server (plan 09). Each Skill is a self-contained folder — instructions and reference files only, no scripts — so it works as part of the Claude Code plugin, copied into `~/.claude/skills/`, zipped for claude.ai, or read by the server's `espn.<workflow>` prompts.

**Skills N.x need server N.x.** Every `SKILL.md` carries `metadata.version` (the package version) and `metadata.tool_contract`; at the start of a session each Skill compares its `tool_contract` with the server's (`espn_get_status` → `server.tool_contract`) and stops when they differ.

**Read-only.** This version has no write module (PHASE W SEAM — NOT IMPLEMENTED): no Skill changes the team; every recommendation ends with how to start the `apply` Skill, which turns an agreed change into numbered manual steps on ESPN. Only the user starts it — the plugin makes it user-invoked (`disable-model-invocation: true`), and Claude Code refuses the model's call for it — so the line names what the user does (guardrail 10): with the plugin, type `/espn-fantasy-football:apply` and the change; with the Skills installed one by one, say *apply* (the copy carries no `disable-model-invocation`, so the model starts `espn-apply`); with only the server's prompts, choose `espn.apply`.

## The eight P0 Skills

| Skill | Use it for | Tools, in order (bare names) |
|---|---|---|
| [onboard](onboard/SKILL.md) | set up and check the league: the format in plain English, which team is the user's, the scoring self-check per stat, the seeding reading, the session state | status → league → roster → box score → (standings / seeding evidence / one auth probe) → record |
| [weekly](weekly/SKILL.md) | the week's plan in six tables: last week, matchup and lineup, the claim or scramble brief, K and D/ST, injuries and byes, league activity | status → league → scoreboards → roster → injuries → projections → lineup → K and D/ST → pool → waivers → schedule → transactions → standings → records |
| [start-sit](start-sit/SKILL.md) | start, sit and flex under the seeding reading; Questionable players; ESPN's projection as a cross-check; the game-day branch once a slot locks | status → league → roster → scoreboard → opponent → injuries → projections → lineup → record; game day: fresh roster → live scoreboard → … → lineup with `only_unlocked` |
| [stream-kdef](stream-kdef/SKILL.md) | which kicker or D/ST to start or stream, two weeks out; claim or free-agent add after the run | status → league → roster → schedule → pool → waivers (one position per call) → record |
| [retro](retro/SKILL.md) | how last week's advice did: regret against two baselines, Brier/CRPS beside ESPN's, "n too small" by name | status → league → scoreboard → retrospective → (box score for a named player) → (transactions) → record |
| [apply](apply/SKILL.md) | the exact clicks for a change agreed in the conversation (user-invoked only) | status → league → roster; nothing logged, nothing changed |
| [session-check](session-check/SKILL.md) | the ESPN session: status, the DevTools steps, `eff setup` in a terminal, one verification — never a cookie in chat | status → (one auth probe) |
| [waivers](waivers/SKILL.md) | claim, pass or marginal against the priority premium; the ordered claim list; the scramble list; the drop with its IR-move option | status → league → roster → pool → injuries → transactions → standings → waivers → record |

Two P0 Skills carry a P1 branch that runs only under `EFF_TOOLSET=full`: `waivers`' usage branch (usage-first detection, the ensemble value basis, the FAAB bid curve) and `start-sit`'s live win probability (`espn_analyze_matchup` with `mode: "live"` beside ESPN's). `weekly` (usage signals, the bye-cluster cost, the league activity digest) and `stream-kdef` (the regressed opponent profiles) name P1 steps too. Under `core` each takes its P0 path and says so.

## Install

- **Claude Code (plugin — the Skills and the server):** from the built runtime clone (`npm ci && npm run build` done; README Quickstart step 5), `claude plugin marketplace add ~/src/espn-fantasy-football-mcp`, then `claude plugin install espn-fantasy-football@espn-fantasy-football-mcp`; in development, `claude --plugin-dir .` on a built checkout. Never from GitHub: the plugin's server runs `dist/cli.js`, a build output git never carries, so a git install's server cannot start. The Skills appear as `/espn-fantasy-football:<name>`.
- **Copy install (instead of the plugin, never beside it):** `node scripts/skills/build-skills.mjs --copy-out dist/skills-copy`, then copy `dist/skills-copy/espn-*` into `~/.claude/skills/` (renamed `espn-<name>` so they never collide with another bundle, every reference to another Skill renamed with it; standard frontmatter only). Register the server under the key `espn-fantasy-football` (`eff print-config --client code`) — the Skills' `disallowed-tools` strings name that key. Beside the plugin, that entry would register the server a second time and list every tool twice.
- **Claude Desktop / claude.ai chat:** zip one `dist/skills-copy/espn-<name>` folder and upload it; configure the server separately (`eff print-config --client desktop`).

## Layout and generation

```text
skills/
├── _shared/references/   the shared text, written once: orient · guardrails · output-template · log ·
│                         tool-outputs · espn-vocabulary · priority-waivers   (not a Skill)
├── <skill>/
│   ├── SKILL.md          frontmatter + body; generated blocks between BEGIN/END GENERATED markers
│   ├── references/       byte-identical copies of _shared/references + the Skill's own <skill>-*.md
│   └── evals/            tool_sequence.json · evals.json · trigger_eval.json
└── README.md
scripts/skills/           manifest.json (tool lists, tool_contract, the eight deny strings, the input
                          contract of every P0 and P1 tool) · _lib.mjs · build-skills.mjs · check-skills.mjs ·
                          tool-sequences.mjs · build-plugin-evals.mjs (the claude plugin eval suite)
```

`node scripts/skills/build-skills.mjs` copies the shared references into every Skill, replaces each generated block in each body (the guardrails in every body; the output contract in every body but `apply` and `session-check`), and stamps `metadata.version` and `metadata.tool_contract`. It is idempotent; `--check` writes nothing and fails when anything is stale. Edit the source, never a copy. The Skills name one another as the plugin installs them — `` `espn-fantasy-football:<name>` ``, never a bare name another bundle's Skill may share (the owner's Yahoo Skills use several of the same names) — and `--copy-out` renames each such reference `espn-<name>` in the copy tree; orient's table gives a prompt-only client the matching `espn.*` prompt.

`node scripts/skills/check-skills.mjs` is Lane 1 (zero tokens, every push) for all thirteen Skills — the P0 Skills validated under `core`, the P1 Skills under `full`, the toolset stated per sequence and per case: the build check; frontmatter (name = folder; description ≤ 350 characters, third person, with "in the user's ESPN league"; `when_to_use`; description + `when_to_use` ≤ 1 536; the listing ≤ 4 600); both guardrail sentences verbatim in every body and the cookie line; the output-contract headings; every `espn_<verb>_…` name a registered tool — in a P0 Skill a P1 tool only on a line labelled `(P1; …)` or `**P1:**`; every P1 Skill's Step 0 carries the toolset stop verbatim; no write tool named anywhere; no qualified tool name in prose; the eight `disallowed-tools` strings; `apply` user-invoked only; every backticked error code a real one; links inside the Skill and one level deep; the eval files well-formed; time-blind triggers with the collision check; every reference to another Skill plugin-qualified (in backticks, naming a Skill of the bundle — never a bare name); every record step's `client_ref` its producer's `meta.request_id`; no identifier under `skills/`, and the repository secret scanner clean.

## Tool sequences (Lane 1 dry run)

`evals/tool_sequence.json` lists the calls a Skill promises, in order, with argument templates on the fixture league `fx-10h` (league id `0`; Team 02 is the user's; Tuesday of week 5).

```text
{ schema_version: 1, skill, tool_contract, toolset: "core" | "full",
  fixture: { league: "fx-10h", env: { EFF_FIXTURE_DIR, ESPN_LEAGUE_ID: "0", EFF_TOOLSET }, team_id, week, … },
  sequences: [ { id, when, fixture_variant?, toolset?: "full", steps: [ { id, tool, args, expect?, note? } ] } ] }
```

- `toolset` is the file's: `core` for a P0 Skill, `full` for a P1 Skill. A P0 Skill's P1 branch is a sequence of its own with `"toolset": "full"` (it must call a P1 tool, and every P1 step the body names is called by one); a P1 Skill's sequences never set one.
- `tool` is a bare tool of the sequence's toolset; `args` validate against the tool's input contract in `scripts/skills/manifest.json` (keys, enums, ranges, the selector variants `selector:single` and `selector:outlook` — the dry run re-validates against the registry's zod schemas).
- `expect` lists the outcomes a step may have on the fixture: `"ok"` (default) or error codes.
- Templates: `{ "$ref": "<step>.<path>" }` (a value from an earlier step's envelope, e.g. `"lineup.data.rec"`); `{ "$source_calls": ["<step>", …] }` (`[{ tool, request_id }]` from those steps); `{ "$opponent": "<scoreboard step>" }` (the other team of the user's matchup); `{ "$player": { "step": "<roster step>", "slot": "FLEX", "eligible": "FLEX", "injury_status": "OUT" } }` (the first player in that slot, optionally eligible for another and carrying ESPN's status); `{ "$player": { "step": "<roster step>", "position": "RB", "rank": 1 } }` (the player a positional reference names — "my RB1" — by orient's **Positional references** rule: the starters at that position ranked by `projection_week_espn`, then the bench; changelog §R10, R10-5); `{ "$ids": { "from": "<step>.<path to an array>", "key": "player_id", "max": 5, "where": { "status": ["FREEAGENT", "WAIVERS"] } } }` (the distinct ids in that list, optionally only the rows whose field holds a listed value — the cascade's available beneficiaries priced as waiver candidates; never resolved empty).
- Every sequence starts with `espn_get_status`; when it records, the record steps come last (log before rendering), each with its producer's kind and its producer's request id as `client_ref` — `{ "$ref": "<producer>.meta.request_id" }` (references/log.md: the key names the result, so a re-run's changed advice is logged and only a retry deduplicates).
- The dry run loads one toolset's sequences with `loadToolSequences(root, { toolset })` — `core` (the default: the eight P0 Skills' P0 paths) or `full` (the five P1 Skills and the P0 Skills' P1 branches), so each server starts with the matching `EFF_TOOLSET`; every file is validated whatever the filter, and anything `check-skills` would reject is refused. It builds arguments with `resolveArgs(step.args, results)` and checks outcomes with `outcomeAllowed(step, outcome)` — all from `scripts/skills/tool-sequences.mjs`.

## Lane 2 cases (`evals/evals.json`)

The skill-creator schema — `{ skill_name, evals: [ { id, name, toolset, prompt, expected_output, files, expectations[], history?, base? } ] }` — with the plan's case name (`ON-1`, `WK-4-E`, `SS-INJ`) beside the integer id. `files` names the fixture the runner stages: `evals/fixtures/fx-10h` or `evals/fixtures/fx-10h/<variant>`, materialised from `fixtures/espn/fx-10h`. Each expectation is one sentence ending with its grader: `(tool_used …)`, `(tool_order)`, `(regex: \`…\`)`, `(regex_absent: \`…\`)` (free) or `(llm)` / `(llm, judge sees both replies)` (paid). A write tool is never named — "No write tool was called" covers all of them. Every Skill has an `-INJ` case whose expected answer equals the base fixture's apart from a quotation and one flag line; refusing to answer fails it. Its `(llm, judge sees both replies)` expectation is judged beside a kept run of its base case — a passing one, else its best-scoring one (changelog §R10, R10-8): the case with the same prompt on a non-injection fixture, or — when the injected text is in the user's message, so no base can share the prompt — the case its `base` names (another case of the same file, not an injection case, on the same toolset; Lane 1 and the build refuse anything else). `toolset` is stated per case: a P0 Skill's cases run under `core` except the ones its rule lists as its P1 branch (`WV-2`, `WV-3-E`, `SS-11-E`, under `full`); a P1 Skill's cases run under `full` except its one `-CORE` case, which runs under `core` and checks the Step 0 stop (a regex expectation on `EFF_TOOLSET=full` — plan 10 B10). `session-check`'s SC-2 prompt carries `<SYNTHETIC_ESPN_S2>`: the runner substitutes a freshly generated cookie-shaped value at run time (never committed) and checks the trace never contains it. `apply` is user-invoked (`disable-model-invocation: true`: the CLI refuses the model), so every one of its prompts is the user typing `/espn-fantasy-football:apply <the agreed change>` — Lane 1 refuses any other. A run is one turn, so a check that belongs to a later turn is its own case with `history`: the earlier turns as `[{ "role": "user", "text" }, { "role": "assistant", "text" }, …]` (user first, alternating, the assistant last, at most 8), and the prompt is the next user turn — plan 09's SC-1 is SC-1 (the first turn: the steps, the question, no probe) and SC-6 (the turn after "done": `espn_check_auth` exactly once and first, `(tool_used: min 1 max 1, first)`). A `(regex: …)` on the final message must be able to fail a reply that prints only orient's mandated opening lines — the Session line of its server's credential state and, while the reading is unconfirmed, the seeding line — so it is anchored to the claim it checks (`(?<!seeding reading )\bunconfirmed\b`, not `unconfirmed`); the build refuses one those lines satisfy, and a `(regex_absent: …)` they would trip (on a case whose Skill hands over to session-check at Step 0 — a private league with a rejected or missing session — the right reply prints no output contract, so a `regex_absent` on its headings is allowed there), unless `MANDATED_LINE_GRADERS` in `scripts/skills/build-plugin-evals.mjs` lists it with its reason (a grader of the one command the Session line itself carries). A case whose seed logs a note (`LOGGED_NOTES`: NC-INJ-2, NC-7, RT-INJ) carries `(tool_used: no input_match on the logged note, arm both)`; the build refuses one without it.

## The plugin eval suite (`claude plugin eval` — Lane 2, plan 10 B15)

`node scripts/skills/build-plugin-evals.mjs` turns every Skill's `evals/evals.json` and `evals/trigger_eval.json` into a `claude plugin eval` suite under `dist/plugin-evals/` (git-ignored; a build output, never committed): one case directory per Lane 2 case and per trigger (`prompt.md` + `graders/*.md`), each expectation's tag mapped mechanically — `(tool_order)` to a `tool_order` grader per consecutive pair of the tools it names, `(tool_used: …)` to `tool_used` on the qualified tool (`input_match <key> <value>` — typed by the tool's input contract in `scripts/skills/manifest.json`, so an array input such as `positions K` or `include contains seeding_evidence` matches the array call the strict schema accepts, `exactly <v> …` matches an array of those elements and nothing else (RT-5's `kinds exactly evidence`), and a key or value no valid call could carry fails the build —, `min`, `max`, `arm`; "every write tool …" to a trace guard; `Skill <name>` to routing; "no input_match on the substituted value / injected string / logged note" to a guard over every tool call's input — the logged note being the one the case's seed wrote), `(regex…)` to `regex` on the final message, `(llm)` to a rubric carrying the case's expected output, and `(llm, judge sees both replies)` to a `baseline` grader: the judge sees the injected run's trajectory beside a kept run of the base case — a passing one, else its best-scoring one (changelog §R10, R10-8) — (the case the injection case's `base` names, else the same prompt on a non-injection fixture; tagged `inj-base`), never a description of it (plan 09 §5.2). `--baselines <results.json>` copies those trajectories in (`baseline/trace.jsonl`) from a run of `--tag inj-base --keep-temp`: a passing kept run of the base case, else its best-scoring kept run (`matches-base` compares the injected reply with the base reply, not with a perfect one — changelog §R10, R10-8), each named with how it was chosen in the suite's README and `baselines-attached.json`; until then — and for an injection case with no base case in the suite — that grader fails. Triggers become `tool_used: Skill` cases for the positives; a negative is a regex over the trace that fails only when its Skill is the first Skill the run calls (another Skill that fired first and handed over to it is routing, not this trigger — changelog §R9); a user-invoked Skill's trigger prompts — its would-be positives (`<skill>--trigger-auto-NN`) included — all assert it never fires on its own. A case with `history` gets a `case.yaml` whose `context.history_file` replays `history.jsonl` (a Claude Code session transcript of the earlier turns). SC-2's `<SYNTHETIC_ESPN_S2>` is replaced by a fresh cookie-shaped value per build.

The harness has no MCP mock layer — a case's plugin starts its servers for real — so "mocks generated from fx-10h" are **eval plugins**: the bundle plus one server, `dist/cli.js serve` in fixture mode on the case's fx-10h variant with `EFF_TEST_STUBS=1` and the no-socket preload, under the toolset the case states. Each plugin's pristine config and cache live in a fresh temp directory outside every git tree (the server refuses one inside), and every server starts through `scripts/skills/eval-server.mjs`, which copies that pristine state into a new temp directory for the start and removes it on exit — so every run of every case begins from the same state, and nothing one run logs reaches another. The launcher also drops every `ESPN_*` and `EFF_*` variable the plugin's `.mcp.json` does not declare (`--keep-env`, written by the build): a variable exported in the shell that runs the suite — an `ESPN_TEAM_ID`, an `EFF_SEEDING_MODE` — never changes the fixture state a case is graded on, and an invalid one never stops its server. `--seed-datasets` seeds every server's cache, `core` and `full` alike (`eff refresh` publishes the same datasets whatever the toolset, and the P0 tools read the schedules and implied totals too; the seed process gets `PATH` and `TMPDIR` — the real temp root that holds the state root, the parent's `TMPDIR` or `/tmp`, which its temp-directory check reads; a `--state` under neither is refused before anything is written, and a failed seed removes the suite); weather is not seeded (no fixture covers fx-10h's week). `--seed` (after `npm run build`) writes the recorded state a case's expected output assumes, through the real tools, into its own plugin: NC-INJ-2's week-4 log entry whose note carries an order, and NC-7's (its base) whose note carries the claim without the order; RT-1 and RT-3's week-4 lineup call; RT-INJ's same call carrying a note, which `espn_analyze_retrospective` returns as that call's `note` (`data.calls[].note`, source `store.recommendation_log` — changelog §R10, R10-13), so RT-INJ grades the note read back as a quoted claim, never followed and copied into no tool argument (`no input_match on the logged note`), beside its variant's JSON team name; RT-4-E's six lineup calls over weeks 1–4 — every lineup call with one scored alternative, the bench QB in the starter's place (changelog §R10, R10-3); SC-4's drifted roster view already read, so Step 0 sees `drift.status: red`; SS-5-E and WK-5-E's points-only reading, recorded by the real `eff setup --seeding points_only`. A fixture-mode server holds no credential: it reports `not_configured`, or the state a variant's manifest scripts (auth-rejected's `rejected`, public-league's `stored`) as a label, with the scripted result of its one `espn_check_auth` — never a value, no request (changelog §R9, R9-3). The user's pending claims follow that label (changelog §R10, R10-21): `not_configured` and `rejected` answer `pending: null` with that state's warning, and `stored` serves the variant's recorded list, so a case that reads them is graded on every variant. A case whose variant stands for any other state, or one held out by name (`HELD_OUT_CASES`), is not written — the build lists it, with the reason, as not testable (SS-6-E is held out until a ruling: on espn-proj-disagree `espn_project_players` weights ESPN 1.0 while untuned, so our mean equals ESPN's and `espn_cross_check` never flags a starter; WV-7-E runs again on auth-rejected, a public league whose stored session ESPN rejected, since orient's `rejected` row carries on there — changelog §R10, R10-7 — and its transaction feed answers keylessly — R10-10; SS-9 and SS-11-E run again on sunday-live, whose London game reads final on a dataset-seeded server since the seed publishes the variant's own pro schedule). Running it costs tokens and is manual: from an empty directory, `claude plugin eval dist/plugin-evals --allow-tools "mcp__plugin_espn-fantasy-football_espn-fantasy-football__*" --no-publish …` (the generated README has the full commands — base cases, `--baselines`, the suite — and the pass bar; a rebuild keeps `evals/results/`).

## Trigger evals (`evals/trigger_eval.json`)

An array of `{ "query", "should_trigger" }` — at least 6 of each, at least 2 negatives naming Yahoo or Sleeper. Every query is time-blind (no weekday, clock time, date, "today", "tonight"): the model is not told the time in Claude Desktop or claude.ai. The four game-day prompts ("who should I start?", "X is inactive, who goes in?", "what can I still change?", "what are my odds right now?") are positives of `start-sit` and of no other Skill.
